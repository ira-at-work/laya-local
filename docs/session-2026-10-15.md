## 3. Laya vs Jev: facts that change design

- **Question schema** (checked against `_check_question` in the installed source): choice uses `criteria` (list or `{label: description}`); score uses `criteria` as an ordered list of level descriptions; noul takes optional `{"true","false"}`. `options=` and `levels=` are rejected.
- **Confidence** is 1 - normalised entropy, not Jev's. The `typed-decisions` checkpoint ships invalid temperatures (clamped to 0.5), so confidence is **uncalibrated** until fitted with `laya.calibrate`.
- **Eval** (`eval.py`, 16 hand-labelled support messages, tiny and self-made): noul refund detection **16/16** (majority baseline 12/16); 4-way department choice **10/16** (some labels debatable). Conclusion: prefer per-class noul questions over wide choice.
- **Weak spots (vendor-reported, unverified by us):** wide choice (Banking77, 77 labels: 0.425), `score` is the weakest type, noul can be biased by its labels, English-only root checkpoint (non-Latin text needs `subfolder="multilingual"`). Option budget is tokens, not a count.
- **CLI** without `--questions` or `--preset` answers the built-in router questions (difficulty/domain/needs_tools/is_sensitive), not your own. On our run its domain confidence was ~0.04.
- Laya's own docs: `laya.serve` exposes Jev's `POST /v1/systemone` wire protocol, so Jev-shaped clients can point at it (unverified that the question shapes are compatible).
- **Open claim to test:** whether several questions sharing one state influence each other. The skill had marked "independent" as unverified; laya_mcp's policy doc says shared JSON state "blends" them and advises putting the relevant text inside each question (reported, untested).

## 6. Recommendation and plan

Install none of the third-party plugins as-is. Reimplement the useful design (hard rules first, allowlist fast path, observe mode default, decision log feeding calibration) in `laya-local` against the pinned install.

1. **Bash-command gate, observe-only (built, see section 7):** resident local process holds the model; a `PreToolUse` hook logs each command with a few per-class noul scores, fails open, never blocks; existing hard stops (`rm -rf`, `git clean`, `sudo`, `--no-verify`) stay deterministic. After 1-2 weeks, label the log, fit temperatures with `laya.calibrate`, measure, and only then consider an "ask" tier.
2. **Offline compaction replay eval:** replay `~/.claude/projects` transcripts, auto-label tool results by whether later turns reference them, score keep/drop before and after calibration. (My idea, not the community's.)
3. **CI failure classifier, advisory only:** flaky vs real, retry cap in code, fit to one repo's history; cache ~840 MB weights on the runner. Vendor CPU figure (~113 ms/question) was on a 56-core machine; a 4-core runner will be slower.

Parked: prompt/model routing (weakest on Laya base checkpoints) and CLAUDE.md rule checking (most rules are deterministic and a grep hook does them better).
