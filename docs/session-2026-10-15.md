## 3. Laya vs Jev: facts that change design

- **Question schema** (checked against `_check_question` in the installed source): choice uses `criteria` (list or `{label: description}`); score uses `criteria` as an ordered list of level descriptions; noul takes optional `{"true","false"}`. `options=` and `levels=` are rejected.
- **Confidence** is 1 - normalised entropy, not Jev's. The `typed-decisions` checkpoint ships invalid temperatures (clamped to 0.5), so confidence is **uncalibrated** until fitted with `laya.calibrate`.
- **Eval** (`eval.py`, 16 hand-labelled support messages, tiny and self-made): noul refund detection **16/16** (majority baseline 12/16); 4-way department choice **10/16** (some labels debatable). Conclusion: prefer per-class noul questions over wide choice.
- **Weak spots (vendor-reported, unverified by us):** wide choice (Banking77, 77 labels: 0.425), `score` is the weakest type, noul can be biased by its labels, English-only root checkpoint (non-Latin text needs `subfolder="multilingual"`). Option budget is tokens, not a count.
- **CLI** without `--questions` or `--preset` answers the built-in router questions (difficulty/domain/needs_tools/is_sensitive), not your own. On our run its domain confidence was ~0.04.
- Laya's own docs: `laya.serve` exposes Jev's `POST /v1/systemone` wire protocol, so Jev-shaped clients can point at it (unverified that the question shapes are compatible).
- **Question independence (tested later, section 8.5):** for two noul questions on the same state, answers were identical to 4 decimals whether asked alone or together (n=400). The claim below was vendor-reported; it did not reproduce for this setup.
- Original vendor claim: whether several questions sharing one state influence each other. The skill had marked "independent" as unverified; laya_mcp's policy doc says shared JSON state "blends" them and advises putting the relevant text inside each question (reported, untested).

## 8. Compaction replay simulation (requested by user)

**Question:** would Laya-driven compaction (score each tool result keep/drop, drop the low scorers) save tokens and time on real Claude Code usage without dropping information the agent later needs? Offline only: nothing was installed in Claude Code, no hook rewrites context.

Code: `compaction/replay.py` (extract and label), `compaction/sample.py` (seeded sample with text), `compaction/score.py` (Laya scoring and metrics). stdlib plus the pinned `laya`. Sample text lives in `/tmp/replay/` (mode 0600, private transcript content, never committed); only aggregate numbers are in this doc. Commits: `Add compaction replay step 1`, `replay: count assistant turns by message id`, `Add compaction replay steps 2-3`.

### 8.1 Data
- 1,808 transcript files under `~/.claude/projects` (49 project dirs); 1,453 contained main-thread tool results. Subagent (sidechain) records are excluded.
- 28,626 tool results, about **14.1M estimated tokens**. Tokens are chars/4, not a tokenizer; no check against recorded API usage was done.
- By tool (tokens): Bash 6.5M (15.9k results), Read 6.2M (4.7k), Edit 0.2M (4.4k), AWS MCP tools and WebFetch/WebSearch/Grep/Agent each under 0.2M.

### 8.2 Labelling method (automatic, crude)
A result's "new anchors" are path/identifier-like tokens (`[A-Za-z0-9_./~-]{8,}`) present in the result but absent from its own call input and from all earlier text in the session. A result is **needed** if any anchor appears later in assistant text or a tool_use input; **needed10** restricts that to the next 10 assistant turns (turns counted by distinct message id).

Bug found by self-review and fixed: the first version counted assistant *records*, but Claude Code writes one record per content block, so "10 turns" meant fewer than 10 real turns. After the fix the within-10-turns figure moved from 65.9% to 56.2%; the never-reused figure (41.1%) did not change. The earlier figure was quoted to the user once, then corrected.

### 8.3 Oracle ceiling (all 28.6k results)
- **41.1%** of result tokens were never reused later; **56.2%** not reused within 10 turns.
- Never reused, by tool: Bash 44.5%, Read 37.9%, Edit 95.6% (tiny volume), `call_aws` 71%, AskUserQuestion 79%, WebSearch 4%, WebFetch 14%, Agent 12%.
- This is the savings available to a *perfect* compactor under this labeler. It is not a measured saving, and the labeler is biased (below).

### 8.4 Label validity (hand check)
I (the model, so not independent) read 20 random sampled results (tool, task, call and the first 170 chars of each result) and judged need. 15 agreed clearly with the automatic label, 4 were ambiguous (information read for understanding, e.g. a README or an issue thread, with no verbatim token reuse later), 0 clear disagreements. Interpretation: `needed` is likely a **lower bound** on true need, so the 41% ceiling is probably overstated. Limits: n=20, judged from truncated heads.

### 8.5 Laya scoring experiment
- Sample: 400 results (seed 0) from a pool of 15,763 results of at least 300 chars. 188 needed (47%), 134 needed10 (34%). Mix: Bash 269, Read 102, other 29.
- State given to the model: last user text (400 chars), tool name, call (300 chars), result (first 1800 + last 700 chars, middle elided), about 1k tokens.
- Question A (keep): "Will the assistant need specific details from this tool result (names, values, errors, code) to continue the task?" Question B (noise): "Is this tool result routine noise ... with nothing needed later?" Both `noul`, pinned `typed-decisions` revision, MPS. Only these two wordings were tried.

**Results (400 results):**

| Signal | AUC vs `needed` | AUC vs `needed10` |
|---|---|---|
| Laya A, P(keep) | **0.544** | **0.536** |
| Laya B, inverted noise prob | 0.483 | 0.474 |
| result size (chars, bigger = keep) | 0.659 | 0.621 |
| new_anchors count | 0.889 | 0.802 |

- Laya A is near chance (0.5). B is at or below chance. A plain size heuristic beats both.
- `new_anchors` is high **by construction**: a result with zero new anchors cannot be labelled needed (25.5% of the sample has zero anchors, 0 of those needed). It does not use future information, so it is computable online, but its AUC is inflated by the labeler and must not be read as proof of a good predictor.
- Score distribution for A: p10 0.504, median 0.542, p90 0.576. Scores sit in a narrow band just above 0.5, so no threshold separates much (uncalibrated; calibration is monotonic and cannot change AUC).
- Threshold sweep (drop if P(keep) < t): t=0.5 drops 30 of 400 results, saving **3.9%** of tokens, while missing 11 needed results (3.2% of needed tokens); drop precision 0.63 against a 0.53 base rate. t=0.4 drops 1 result. t=0.6 drops 389 of 400 (97% of tokens saved, 99% of needed tokens lost). There is no threshold with a useful trade-off.
- **Latency:** median **221 ms** per result for one question (p90 305 ms), versus about 25 ms per question on the earlier ~200-token benchmark. Latency scales with input length. Scoring a 100-result compaction would take about 22 s; scoring all 28.6k results about 1.7 h. Any time saving from a shorter context would have to beat that.
- **Question independence (resolves an open item):** the keep-probability from the single-question call and from the two-question call differed by a mean and max of 0.0000 (all 400 results). Within this test (two noul questions, same state), co-asked questions did not influence each other. This contradicts the laya_mcp "blending" warning for this setup; it does not rule out interaction for choice/score types or larger sets.

### 8.6 Conclusion
1. **Do not install Laya-based compaction.** Zero-shot `typed-decisions` keep/drop is not distinguishable from chance on this data (AUC 0.54), and a one-line size heuristic is better (0.66). The only measured threshold that drops anything meaningful (t=0.6) loses essentially all needed content.
2. A real ceiling exists (up to about 41% of tool-result tokens never reused, probably overstated), concentrated in Bash and Read output. Capturing it needs either a fine-tuned scorer trained on these labels, or deterministic rules (cap or trim large Bash output, drop successful-edit acknowledgements). That is a different project and was not attempted.
3. The user's question about an on/off switch is moot until a scorer beats the size baseline, so `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` was not investigated and remains unverified.
4. Vendor claims about Laya compaction (laya-compaction, fast-systemone-compaction) were reported without measured savings; this experiment is the only measurement we have, and it is negative for the zero-shot model.

### 8.7 Threats to validity (for the blog post)
- Labels are automatic and biased toward verbatim token reuse; understanding-only reads are labelled unneeded. This penalises every scorer, including a perfect one.
- Hand check was by the same model family that wrote the labeler, n=20.
- One sample of 400, one seed, no confidence intervals (AUC standard error at n=400 is roughly 0.03, so 0.54 versus 0.50 is within noise).
- Two question wordings, one truncation scheme. A better prompt, richer state (e.g. whether later edits touch the file) or the multilingual/fine-tuned checkpoints were not tried.
- Single user's workload (infra, Terraform, spec-driven development, many skill-injected prompts); the "task" text is often a skill preamble, not the real goal, which likely hurts the model.
- Subagent traffic excluded; token counts are estimates; transcripts of a currently running session changed result counts slightly between runs (28,615 to 28,626).
- Laya's own docs say zero-shot decision quality is limited and recommend fitting on your data; this result is consistent with that.
